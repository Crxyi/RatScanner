Know what a file does
before you run it.

Drop a .jar, .exe or script. Every class is taken apart with Vineflower, CFR and ASM bytecode analysis and checked for RATs, token stealers, loaders, miners, /pay stealers, backdoors and malware that gets installed later.

Files are never executed – not on our server and not on your PC. We only read the bytes.

Scan by URL

Downloaded server-side. Private, loopback and cloud metadata addresses are refused.

Check a hash

Shows whether the file was scanned here before and what the verdict was.

Three engines

Vineflower and CFR give two independent decompilations – where one fails, the other helps. ASM reads the raw bytecode, which no obfuscator can hide.

Hidden strings

Base64, hex, reversed, byte-array and character-by-character encrypted strings are rebuilt by emulation before they are checked – the trick SilentNet uses to hide its servers.

Behaviour, not names

Combination rules detect what code does: download + run, read token + webhook, chat event + setOp, send chat + /pay, relaunch as hidden process – even when split over many classes.

      How the scan works

      1. Unpacking. JARs are read exactly like the JVM reads them. Nested JARs (Fabric jar-in-jar, shading) are scanned up to 3 levels deep. Disguised classes, hidden EXE/DLL files, scripts and encrypted blobs are detected.
      2. ASM bytecode. Every instruction of every method is read: calls (Runtime.exec, URLClassLoader, defineClass, Session.getAccessToken, sendChatCommand, setOp …), constants, invokedynamic arguments.
      3. String emulation. A small emulator rebuilds strings that are hidden with Base64, hex, byte arrays or character arithmetic like (char)(47932 - 47815), then checks them again.
      4. Vineflower + CFR. Suspicious and own classes are decompiled with both decompilers and the source is checked again. Everything else is decompiled on demand when you open it.
      5. Programs (.exe, .dll, ELF, Mach-O). PE headers, sections, imports and packers (UPX, Themida, VMProtect, PyInstaller) are analysed, all ASCII and UTF-16 strings are checked, and JARs embedded in programs are unpacked and scanned with all Java engines.
      6. Combinations. Single capabilities are often harmless – the combination is what matters. Over 35 rules link capabilities inside a class and across the whole file.
      7. Verdict. Critical findings → Malicious, strong signs → Suspicious, weak signs → Caution, otherwise Clean.

      Never executed

      Uploaded files are only ever read as bytes. The server never runs them, never loads them as Java classes and never offers them for download – so the scan itself can never infect anyone.

      Limits

      A static scan can never prove a file is safe. Heavily obfuscated code, code that is downloaded later or brand new tricks can slip through. Only run files from sources you trust.
